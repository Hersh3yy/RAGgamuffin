+# RAGgamuffin
+
+A local-first, multi-agent pipeline that turns raw, messy coding notes into a
+pristine, structured Obsidian knowledge base — running entirely on local
+models (llama.cpp via Msty / Msty Claw). No data leaves your machine.
+
+> **Full documentation with visuals**: open
+> [docs/documentation.html](docs/documentation.html) in a browser — covers the
+> pipeline, wiki loop, user flow, Obsidian guide for rookies, Msty setup
+> checklist, logging design, and FAQ. For how Msty Claw itself works, open
+> [docs/claw-guide.html](docs/claw-guide.html).
+
+## How it works
+
+```mermaid
+flowchart LR
+    rawNote["Raw note in 01_unprocessed"] --> watcher["Claw watcher task"]
+    watcher --> a1["Agent 1: Verifier"]
+    a1 --> a2["Agent 2: Structurer"]
+    a2 --> a7["Agent 7: Linguist"]
+    a7 --> a3["Agent 3: Visualizer"]
+    a3 --> a4["Agent 4: Critic"]
+    a4 -->|"final doc"| processed["02_processed"]
+    a4 -->|"gaps"| backlog["03_meta/backlog.md"]
+    processed -.->|"future: MCP server"| cursorIDE["Cursor"]
+```
+
+| Agent | Job | Prompt |
+|---|---|---|
+| 1 Verifier | Fact-checks prose against the code in the note; flags contradictions with callouts | [agents/agent1-verifier.md](agents/agent1-verifier.md) |
+| 2 Structurer | Business logic first, code hidden in `<details>` toggles, Dutch/English protocol, `[[wiki links]]` | [agents/agent2-structurer.md](agents/agent2-structurer.md) |
+| 7 Linguist | Dutch language QA: validates translations, keeps technical terms in English | [agents/agent7-linguist.md](agents/agent7-linguist.md) |
+| 3 Visualizer | Injects Obsidian-safe Mermaid diagrams, changes nothing else | [agents/agent3-visualizer.md](agents/agent3-visualizer.md) |
+| 4 Critic | Final QA gate; repairs mechanical defects, writes the doc, logs gaps to the backlog | [agents/agent4-critic.md](agents/agent4-critic.md) |
+| 5 Curator | Scheduled wiki gardener: adds missing links, reports missing documents and reader questions | [agents/agent5-curator.md](agents/agent5-curator.md) |
+| 6 Consultant | Interactive ticket triage: paste a ticket, get a KB-grounded plan plus an explicit missing-info list | [agents/agent6-consultant.md](agents/agent6-consultant.md) |
+| 8 Sentinel | Weekly git diff check: changelog since last commit, flags stale KB documents | [agents/agent8-sentinel.md](agents/agent8-sentinel.md) |
+
+Agents 1, 2, 7, 3, 4 form the automated per-note pipeline. The Curator and
+Sentinel run on weekly schedules (separate playbooks). The Consultant is a chat
+skill you talk to directly — in Msty with a Knowledge Stack, or in Cursor via MCP.
+
+## Repo layout
+
+```
+agents/         system prompts (source of truth — paste into Msty Skills Studio)
+claw/           Msty Claw orchestration guide (bot, playbooks, watcher, security)
+docs/           documentation.html (main docs) + claw-guide.html (Claw explained)
+vault/          the Obsidian vault (open THIS folder as a vault in Obsidian)
+  01_unprocessed/   drop raw notes here          (contents NOT committed)
+  02_processed/     pipeline output lands here   (contents NOT committed)
+  03_meta/          backlog, changelogs, archive, daily logs (template files committed)
+```
+
+## Privacy model: what git sees
+
+The repo is the **pipeline**, not the **knowledge**:
+
+- Committed: prompts, docs, folder structure, the empty backlog template.
+- Ignored: all note contents in `01_unprocessed/` and `02_processed/`, plus
+  `.obsidian/` machine state. Your work notes (which may contain company code)
+  never end up on a personal remote.
+
+Syncing the actual vault content on the work machine is a separate concern —
+use whatever your company approves (an internal git remote for the `vault/`
+folder, a synced network drive, or Obsidian Sync with company blessing). Do
+NOT just flip the `.gitignore` and push company code to a personal GitHub.
+
+## Setup on a fresh machine (home or work)
+
+1. Clone this repo.
+2. Open **the `vault/` folder** as a vault in Obsidian (Open folder as vault).
+   Each machine gets its own `.obsidian/` state; that is intentional.
+3. Install Msty Claw and your llama.cpp models (Gemma / Qwen).
+4. Follow [claw/playbook.md](claw/playbook.md) step by step: providers, bot,
+   security, skills, playbook, manual validation, then the watcher.
+5. Drop a note into `vault/01_unprocessed/` and watch the assembly line go.
+
+## Usage
+
+- Write raw notes as `.md` files into `vault/01_unprocessed/`. Messy is fine —
+  that is the whole point. Include the relevant code snippets in the note;
+  Agent 1 can only verify claims against code it can see.
+- Keep notes focused: one topic per note. Many small notes beat one epic
+  (small local models have small context windows).
+- Check `vault/03_meta/backlog.md` periodically and resolve flagged gaps.
+
+## Future: MCP server for Cursor
+
+Once `02_processed/` has content, expose it to Cursor as read-only context via
+the filesystem MCP server. In Cursor: Settings > MCP, or `.cursor/mcp.json` in
+the project where you want the knowledge available:
+
+```json
+{
+  "mcpServers": {
+    "raggamuffin-kb": {
+      "command": "npx",
+      "args": [
+        "-y",
+        "@modelcontextprotocol/server-filesystem",
+        "/absolute/path/to/RAGgamuffin/vault/02_processed"
+      ]
+    }
+  }
+}
+```
+
+Point it at `02_processed` only — the agent gets the curated knowledge, not
+the raw mess. Adjust the absolute path per machine.
+
+## Things to know before going all-in
+
+- Small local models WILL occasionally break the output contract (preambles,
+  stray code fences). Agent 4 exists precisely to catch this — never skip it.
+- Process one file per run. Batch-processing with 4B-class models degrades
+  output badly as context fills up.
+- Content inside `<details>` toggles is not indexed the same as regular text
+  by some Obsidian plugins/search. Acceptable tradeoff for readability, but
+  know it is there.
+- Test the full chain manually on 2-3 sample notes before enabling the
+  watcher task. See step 6 of the Claw guide.
+- The prompt files in `agents/` are the source of truth. Edit there, commit,
+  re-paste into Skills Studio on each machine — otherwise machines drift.

+# Agent 1 — Verifier
+
+> Paste everything below the `---` line into Msty Skills Studio as the skill
+> instructions (SKILL.md body) for the **Verifier** skill.
+>
+> Recommended model settings: temperature 0.3, top_p 0.9.
+> Use system prompt mode **Replace**.
+
+---
+
+You are THE VERIFIER, the first agent in an automated documentation pipeline. You receive a raw, unstructured markdown coding note. Your job is to fact-check the prose claims against the code snippets contained in the SAME note, then pass the note onward with verification annotations.
+
+## OUTPUT CONTRACT (absolute rules)
+
+1. Your entire response is the annotated markdown note itself. No preamble, no closing remarks, no explanation of what you did.
+2. NEVER wrap the whole document in a code fence.
+3. Preserve the original note's text and code EXACTLY. You only ADD annotations; you never rewrite, fix, reorder, or delete anything.
+
+## VERIFICATION RULES
+
+Compare every factual claim in the prose against the code in the note:
+
+- Function/class/file names mentioned in prose: do they match the code?
+- Described behavior (return values, side effects, conditions, defaults): does the code actually do that?
+- Numbers in prose (timeouts, limits, retries, intervals): do they match the code?
+- Described flow order (first X, then Y): does the code agree?
+
+When a claim CONTRADICTS the code, insert this Obsidian callout on its own line directly below the claim:
+
+> [!warning] VERIFY: <one sentence: what the prose says vs. what the code shows>
+
+When a claim cannot be checked against anything in the note (references external systems or missing code), and it looks important, insert:
+
+> [!note] UNVERIFIED: <one sentence: what is claimed and why it could not be checked>
+
+## CONSTRAINTS
+
+- NEVER silently "fix" prose or code. Discrepancies are flagged, not corrected. A wrong correction is worse than a flagged doubt.
+- Maximum 5 callouts total. Flag only the most significant issues; this is triage, not an audit.
+- If everything checks out, return the note completely unchanged.
+- Do not add callouts inside code fences.
+
+## EXAMPLE
+
+Input:
+
+the sync runs every 10 minutes via the scheduler
+```php
+$schedule->command('stock:sync')->everyFiveMinutes();
+```
+
+Correct output:
+
+the sync runs every 10 minutes via the scheduler
+
+> [!warning] VERIFY: Prose says the sync runs every 10 minutes, but the code schedules `stock:sync` every 5 minutes.
+
+```php
+$schedule->command('stock:sync')->everyFiveMinutes();
+```
+
+Respond with the annotated note only.

+
+<details>
+<summary>Technical Implementation</summary>
+
+```python
+# code goes here
+```
+
+</details>
+

+---
+
+You are THE VISUALIZER, a diagram-injection machine in an automated pipeline. You receive a fully structured markdown document. Your ONLY job is to insert native Mermaid diagrams where they genuinely clarify the content, and return the complete document.
+
+## OUTPUT CONTRACT (absolute rules — violating any of these breaks the pipeline)
+
+1. Your entire response is the final markdown document itself.
+2. NEVER write a preamble or closing remark. NEVER explain your changes.
+3. NEVER wrap the whole document in a code fence.
+4. The first character of your response is `#`.
+5. You return the input document 100% UNCHANGED except for inserted mermaid blocks. Do not reword, reorder, fix, translate, or delete ANY existing text, headings, links, callouts, toggles, or code. You are not an editor. You only insert diagrams.
+
+## WHEN TO INSERT A DIAGRAM
+
+- A section describes a process, decision flow, or pipeline with 3+ steps → insert a `flowchart TD` directly after that section's explanatory paragraph.
+- A section describes interactions between 2+ actors/systems over time (requests, callbacks, queues, webhooks) → insert a `sequenceDiagram`.
+- Minimum 1 diagram, maximum 3 per document. If truly nothing qualifies, insert exactly one flowchart summarizing the `## Samenvatting`.
+- NEVER insert a diagram inside a `<details>` toggle, inside a code fence, or between `<summary>` and `</details>`.
+- Diagram node labels and notes use the same language as the surrounding section (Dutch for business sections, English for technical sections). Keep technical terms in English.
+
+## MERMAID SYNTAX RULES (Obsidian-safe — follow exactly)
+
+1. Only two diagram types are allowed: `flowchart TD` (or `flowchart LR`) and `sequenceDiagram`.
+2. Node IDs: letters, digits, underscores ONLY. No spaces, no hyphens. Good: `checkStock`, `erp_sync`. Bad: `check stock`.
+3. Never use these words as node IDs: `end`, `graph`, `subgraph`, `flowchart`, `class`, `style`. Use `endNode`, `processEnd` instead.
+4. Any label containing spaces, parentheses, colons, commas, or quotes goes in square brackets with double quotes: `A["Order ontvangen (API)"]`.
+5. Edge labels with special characters get double quotes: `A -->|"max 5 min"| B`.
+6. NO `style`, `classDef`, `linkStyle`, `:::`, or color/fill of any kind. Theme colors are automatic.
+7. NO `click` events, NO HTML, NO `<br>` in labels. Keep labels under 6 words.
+8. Subgraphs: `subgraph sg1 ["Label Here"]` ... `end` — explicit ID plus quoted label.
+9. sequenceDiagram participants: `participant ERP` or `participant ws as "Warehouse System"`. Arrows: `->>` for calls, `-->>` for responses.
+10. Maximum 10 nodes per flowchart. Simplify rather than cram.
+
+The diagram block must be fenced exactly like this, with blank lines before and after the fence:
+
+```mermaid
+flowchart TD
+    A["Voorraadupdate ontvangen"] --> B{"Debounce actief?"}
+    B -->|"ja"| C["Bundel update"]
+    B -->|"nee"| D["Start debounce window"]
+    C --> E["Upsert naar database"]
+    D --> E
+```
+

+
+1. Copy `03_meta/sentinel-state.template.md` → `03_meta/sentinel-state.md`.
+2. Set `code_repo` to `<CODE_REPO>` and `branch` to `main` or `master`.
+3. Add `<CODE_REPO>` to Allowed Folders as **read-only** (section 3).
+4. Leave `last_commit` empty for the first run — the playbook records HEAD.
+
+Create playbook `kb-sentinel-check`:
+
+1. **Read state** from `03_meta/sentinel-state.md` (`last_commit`, `code_repo`, `branch`).
+2. **Git metadata** (via Claw shell in `<CODE_REPO>`, read-only):
+   - If `last_commit` is empty: `git rev-parse HEAD` and `git log -20 --oneline`.
+   - Else: `git log <last_commit>..HEAD --oneline` and `git diff --stat <last_commit>..HEAD`.
+   - If no new commits: write a one-line note to today's log and stop.
+3. **Build KB_INDEX**: list all `.md` filenames in `02_processed/`.
+4. **Agent 8**: run skill `kb-sentinel` with four labeled inputs: STATE,
+   COMMITS, DIFF_SUMMARY, KB_INDEX.
+5. **Write results** — split Sentinel output on markers:
+   - Changelog (above `=== BACKLOG ===`) → `03_meta/changelogs/<YYYY-MM-DD>.md`
+   - Backlog entries (between `=== BACKLOG ===` and `=== STATE ===`) → append under `## Open` in `03_meta/backlog.md`
+   - State block (after `=== STATE ===`) → overwrite `03_meta/sentinel-state.md`
+6. **Log**: `sentinel check: N commits, M stale docs flagged`.
+
+Scheduling: weekly (e.g. Monday morning). Run manually after a big release.
+
+**Your workflow when `#stale-doc` appears:** find the archived raw note in
+`03_meta/archive/`, update it with what changed, copy back to
+`01_unprocessed/` — the pipeline re-processes and overwrites the processed doc.
+
+## Reprocessing (nudging) a note
+
+The pipeline touches each file exactly once: process → archive. It never
+re-analyzes on its own. To re-analyze deliberately:
+
+1. Edit the archived raw note in `03_meta/archive/` (add the new info there —
+   raw notes are the source of truth, processed docs get overwritten).
+2. Copy it back into `01_unprocessed/`.
+3. The watcher picks it up; the new output OVERWRITES the existing file in
+   `02_processed/` (same filename), so links from other notes keep working.
+
+To merge topics: combine the raw notes into one file yourself, drop it in the
+inbox, and delete the superseded documents from `02_processed/`.
+
+## Failure modes to expect
+
+- **Agent output wrapped in a code fence or preceded by chatter**: Agent 4 strips this, but if a file in `02_processed/` ever starts with anything but `#`, the Critic missed it — re-run that file.
+- **Broken mermaid**: open the note in Obsidian; the mermaid block shows a parse error inline. Fix by hand or re-run Agent 3 on the document in a normal chat.
+- **Context overflow on long notes**: split the raw note into two smaller notes. Prefer many small notes over one epic.
+- **Model swaps**: after changing which model backs a skill, redo step 6 from scratch. Different models break contracts in different ways.

+  <h2>The mental model</h2>
+  <div class="card">
+    <p><strong>Msty Studio</strong> is the chat app. <strong>Msty Claw</strong> is its agent sibling: a desktop app where AI doesn't just answer — it <em>does things</em>: reads and writes files, runs multi-step workflows, on a schedule, with guardrails. RAGgamuffin lives entirely in Claw.</p>
+    <p>Claw's design philosophy: every automated action runs inside explicit boundaries you set up front — which folders, which network access, which approvals. You define the cage first, then let the agent loose inside it.</p>

+    task["Task - schedule or watcher"] --> playbook
+    security["Security - folders, network, approvals"] --> bot
+    bot --> actions["File reads and writes in the vault"]
+    actions --> activity["Activity - run history"]

+  <table>

+<section id="run">
+  <h2>Anatomy of a run</h2>
+  <p>What actually happens when the watcher fires on a new note:</p>
+
+  <pre class="mermaid">
+sequenceDiagram
+    participant T as Task_Watcher
+    participant P as Playbook
+    participant S as Security
+    participant K as Skills
+    participant V as Vault
+    T->>P: new file detected
+    P->>S: may I read 01_unprocessed?
+    S-->>P: allowed folder - yes
+    P->>K: verifier, structurer, visualizer, critic - in order
+    K-->>P: final document plus backlog section
+    P->>S: may I write 02_processed and 03_meta?
+    S-->>P: yes - or approval prompt if enabled
+    P->>V: write doc, append backlog, append log, archive source
+  </pre>
+  <p class="diagram-caption">Every file operation passes the security layer. With approvals on, Claw asks you before writing — that's the prompt you'll see during your first runs.</p>
+
+  <div class="card">
+    <p><strong>Where to watch it happen:</strong> every bot has an <em>Activity</em> view — the full history of what ran, what it read and wrote, and any errors. This is your forensics tool; the daily logs in <code>03_meta/logs/</code> are your lightweight summary. Check Activity when a run misbehaves, logs when you just want to know what happened today.</p>

+<section id="daily">
+  <h2>Day-to-day operation</h2>
+
+  <table>
+    <tr><th>You want to...</th><th>Do this in Claw</th></tr>
+    <tr><td>Process notes</td><td>Nothing — drop files in <code>01_unprocessed/</code> and the watcher handles it</td></tr>
+    <tr><td>Run the pipeline right now</td><td>Open the <code>kb-process-note</code> playbook → Run. It exits immediately if the inbox is empty</td></tr>
+    <tr><td>Audit the wiki now</td><td>Run <code>kb-curate</code> manually</td></tr>
+    <tr><td>Check if KB is stale vs code</td><td>Run <code>kb-sentinel-check</code> manually or wait for the weekly task; read <code>03_meta/changelogs/</code></td></tr>
+    <tr><td>Triage a ticket</td><td>Open a chat with the <code>kb-consultant</code> skill, paste the ticket. Attach the Knowledge Stack for automatic retrieval</td></tr>
+    <tr><td>See what ran today</td><td>Open <code>03_meta/logs/&lt;today&gt;.md</code> in Obsidian — or the bot's Activity view for full detail</td></tr>
+    <tr><td>Pause the automation</td><td>Disable the watcher task (Tasks screen). Files just queue up in the inbox; nothing is lost</td></tr>
+    <tr><td>Improve a prompt</td><td>Edit the file in the repo's <code>agents/</code>, commit, re-paste into the skill on each machine. Repo is the source of truth</td></tr>
+    <tr><td>Test a prompt change safely</td><td>Clone the bot or skill, test on a sample note, then promote the change</td></tr>
+  </table>
+
+  <h3>Approvals: what to expect at first</h3>
+  <div class="card">
+    <p>With the recommended baseline, Claw will interrupt and ask permission for file writes during your first runs. This is intentional — you're verifying the pipeline writes exactly where it should (<code>02_processed/</code>, <code>03_meta/</code>) and nowhere else. After several clean runs, relax approvals for writes inside the vault and the pipeline becomes fully hands-off.</p>
+  </div>
+
+  <h3>The golden rules</h3>
+  <ul>
+    <li>One bot, one purpose. Don't bolt unrelated jobs onto the KB bot — make a new bot.</li>
+    <li>Security before skills, manual runs before watchers. Always.</li>
+    <li>Never widen Allowed Folders to fix an error; figure out why the playbook tried to write outside the vault instead.</li>
+    <li>After swapping which model backs a skill, re-validate with manual runs — different models break formatting contracts in different ways.</li>
+  </ul>

+  <h2>Troubleshooting</h2>
+
+  <table>
+    <tr><th>Symptom</th><th>Likely cause</th><th>Fix</th></tr>
+    <tr><td>Nothing happens when I drop a file</td><td>Watcher task disabled, or bot stopped</td><td>Check Tasks screen; run the playbook manually as a test; check Activity for errors</td></tr>

+<section id="what">
+  <h2>What is this?</h2>
+  <div class="card">
+    <p>You write rough notes while coding — half sentences, pasted snippets, "remember this gotcha". They pile up and become useless. RAGgamuffin fixes that:</p>
+    <p>You drop a raw note into a folder. Local AI agents (running via llama.cpp inside Msty Claw) take turns improving it. A finished, structured document appears in your Obsidian vault, with business logic up top, Dutch prose checked, technical code tucked into collapsible toggles, key concepts linked together, and diagrams where they help.</p>
+    <p><strong>Local-first means private.</strong> The models run on your own machine. Company code in your notes never touches a cloud API.</p>
+  </div>
+
+  <pre class="mermaid">
+flowchart LR
+    you(("You")) -->|"drop messy note"| inbox["01_unprocessed"]
+    inbox --> pipeline["Per-note pipeline"]
+    pipeline -->|"clean document"| kb["02_processed"]
+    pipeline -->|"gaps and questions"| meta["03_meta backlog"]
+    kb --> obsidian["Browse in Obsidian"]
+    kb -.->|"later"| cursor["Cursor via MCP"]
+  </pre>
+  <p class="diagram-caption">The big picture: one folder in, two folders out.</p>
+</section>

+<section id="how">
+  <h2>How it works: the assembly line</h2>
+
+  <table>
+    <tr><th>Agent</th><th>Role</th><th>What it does</th><th>What it must NOT do</th></tr>
+    <tr><td><span class="pill">1</span>Verifier</td><td>Fact-checker</td><td>Compares your prose claims against the code in the note; flags contradictions with warning callouts</td><td>Never silently fixes anything</td></tr>
+    <tr><td><span class="pill">2</span>Structurer</td><td>Editor</td><td>Business logic first in Dutch with English translations, code hidden in collapsible toggles, key concepts wiki-linked</td><td>Never changes code content</td></tr>
+    <tr><td><span class="pill">7</span>Linguist</td><td>Dutch QA</td><td>Validates Dutch business prose, first-use translations, and that technical terms stay in English</td><td>Never touches code, toggles, or mermaid</td></tr>
+    <tr><td><span class="pill">3</span>Visualizer</td><td>Illustrator</td><td>Inserts Mermaid flowcharts and sequence diagrams where they clarify</td><td>Never rewords a single sentence</td></tr>
+    <tr><td><span class="pill">4</span>Critic</td><td>Quality gate</td><td>Repairs mechanical formatting defects, writes the final file, reports knowledge gaps to the backlog</td><td>Never touches meaning or code</td></tr>
+    <tr><td><span class="pill">5</span>Curator</td><td>Wiki gardener (scheduled)</td><td>Audits one document at a time: adds missing wiki links, reports missing documents and reader questions</td><td>Never changes anything except adding links</td></tr>
+    <tr><td><span class="pill">6</span>Consultant</td><td>Ticket triage (interactive)</td><td>You paste a ticket; it proposes a plan grounded in the knowledge base and lists what info is missing</td><td>Never presents a guess as knowledge</td></tr>
+    <tr><td><span class="pill">8</span>Sentinel</td><td>Code watcher (weekly)</td><td>Compares git commits since last check against the KB; writes a changelog and flags stale documents</td><td>Never pastes code diffs or secrets into logs</td></tr>
+  </table>
+  <p class="diagram-caption">Agents 1, 2, 7, 3, 4 are the per-note pipeline. Agents 5 and 8 run on a schedule. Agent 6 is interactive.</p>
+
+  <pre class="mermaid">
+sequenceDiagram
+    participant W as Watcher
+    participant A1 as Agent1_Verifier
+    participant A2 as Agent2_Structurer
+    participant A7 as Agent7_Linguist
+    participant A3 as Agent3_Visualizer
+    participant A4 as Agent4_Critic
+    participant V as Vault
+    W->>A1: raw note text
+    A1->>A2: note plus VERIFY flags
+    A2->>A7: structured document
+    A7->>A3: Dutch-validated document
+    A3->>A4: document plus diagrams
+    A4->>V: write final doc to 02_processed
+    A4->>V: append gaps to backlog
+    A4->>V: append run entry to daily log
+  </pre>
+  <p class="diagram-caption">One pipeline run, from raw note to finished document. Each agent only sees the previous agent's output.</p>
+
+  <h3>Why a chain of small agents instead of one big prompt?</h3>
+  <div class="card">
+    <p>Small local models (4B-class Gemma/Qwen) do one job well and many jobs badly. Splitting the work means each agent gets a short, strict instruction set and a small context. It also means failures are isolated: if diagrams break, you re-run Agent 3, not the whole thing.</p>
+  </div>
+
+  <h3>What a finished document looks like</h3>
+  <pre class="mermaid">
+flowchart TD
+    title["H1 Title"] --> samenvatting["Samenvatting - business summary, no code"]
+    samenvatting --> kern["Kernconcepten - linked core concepts"]
+    kern --> sections["Topic sections - explanation first"]
+    sections --> toggle["Collapsible toggle - code hidden inside"]
+    sections --> diagram["Mermaid diagram"]
+    sections --> vragen["Open Vragen - unresolved flags"]
+  </pre>
+  <p class="diagram-caption">Document anatomy: skim the top, expand toggles only when you need the code.</p>
+</section>

+<section id="wiki">
+  <h2>The wiki loop: Curator and Consultant</h2>
+
+  <div class="card">
+    <p>Processing notes one by one gives you good <em>documents</em>. Two more agents turn those documents into a <em>wiki</em> — an interlinked, self-improving knowledge network.</p>
+  </div>
+
+  <h3>The Curator (Agent 5) — scheduled gardening</h3>
+  <p>On a schedule (weekly) or on demand, the Curator picks one processed document and audits it against the entire knowledge base index:</p>
+  <ul>
+    <li><strong>Adds missing links:</strong> if a document mentions a concept that another document covers, but doesn't link it, the Curator inserts the <code>[[link]]</code>. The graph gets denser over time, automatically.</li>
+    <li><strong>Finds promised-but-missing documents:</strong> links pointing at documents that don't exist become <code>#missing-doc</code> backlog entries — your writing TODO list.</li>
+    <li><strong>Asks reader questions:</strong> things a reader would wonder after this document that nothing in the base answers become <code>#open-question</code> entries. Answer them yourself or hand them to another LLM, then drop the answer into the inbox as a new note.</li>
+  </ul>
+
+  <pre class="mermaid">
+flowchart TD
+    schedule["Weekly task or manual run"] --> pick["Curator picks one document"]
+    pick --> audit["Audit against index of all titles"]
+    audit --> links["Insert missing wiki links"]
+    audit --> gaps["Report missing documents"]
+    audit --> questions["Raise reader questions"]
+    gaps --> backlog["Backlog"]
+    questions --> backlog
+    backlog --> you(("You answer or research"))
+    you --> newNote["New raw note in inbox"]
+    newNote --> pipeline["Pipeline processes it"]
+    pipeline --> denser["Knowledge base grows and interlinks"]
+    denser --> pick
+  </pre>
+  <p class="diagram-caption">The self-improving loop: every audit produces either better linking or new writing prompts. The wiki literally tells you what to write next.</p>
+
+  <h3>The Consultant (Agent 6) — paste a ticket, get a grounded plan</h3>
+  <p>An interactive skill, not a pipeline stage. Open a chat with it in Msty (with a Knowledge Stack built from <code>02_processed/</code> attached), paste a ticket or task, and it answers in a fixed format:</p>
+  <ol>
+    <li><strong>Wat ik begrijp</strong> — its interpretation of the ticket</li>
+    <li><strong>Voorgestelde aanpak</strong> — a concrete plan, citing the knowledge base documents it used</li>
+    <li><strong>Aannames</strong> — every assumption it had to make, explicitly</li>
+    <li><strong>Ontbrekende informatie</strong> — what's missing and who can answer it; structural gaps become <code>#ticket-gap</code> backlog entries</li>
+  </ol>
+
+  <pre class="mermaid">
+flowchart LR
+    ticket["You paste a ticket"] --> consultant["Consultant skill"]
+    kb["Knowledge Stack from 02_processed"] --> consultant
+    consultant --> plan["Grounded plan of attack"]
+    consultant --> missing["Explicit missing-info list"]
+    missing --> backlog["Ticket gaps to backlog"]
+    backlog --> improve["Knowledge base improves where reality demanded it"]
+  </pre>
+  <p class="diagram-caption">Real tickets expose the most valuable gaps: knowledge you actually needed and didn't have.</p>
+
+  <div class="card">
+    <p><strong>Same trick inside Cursor:</strong> with the filesystem MCP server pointed at <code>02_processed/</code> (see README), paste the ticket into Cursor chat and tell it to consult the knowledge base before answering and to list missing information explicitly. Your KB becomes IDE context.</p>
+  </div>
+
+  <h3>The Sentinel (Agent 8) — weekly code diff check</h3>
+  <p>The codebase moves; the knowledge base can go stale. Once a week the Sentinel compares git history on your work repo against the last commit it checked, writes a changelog, and flags KB documents that likely need updating.</p>
+
+  <pre class="mermaid">
+flowchart TD
+    weekly["Weekly scheduled task"] --> state["Read last_commit from sentinel-state"]
+    state --> git["Git log and diff since last commit"]
+    git --> sentinel["Sentinel matches changes to KB titles"]
+    sentinel --> changelog["Write changelog to 03_meta/changelogs"]
+    sentinel --> stale["Flag stale docs on backlog"]
+    sentinel --> update["Update last_commit in state"]
+    stale --> you(("You update raw note"))
+    you --> inbox["Drop back in 01_unprocessed"]
+    inbox --> fresh["Pipeline re-processes doc"]
+  </pre>
+  <p class="diagram-caption">The KB stays tied to the code. Stale-doc backlog entries tell you exactly what to refresh.</p>
+
+  <p>Setup: copy <code>sentinel-state.template.md</code> to <code>sentinel-state.md</code>, point <code>code_repo</code> at your Laravel/project repo (not RAGgamuffin itself), add that repo to Claw Allowed Folders as read-only. Full steps in <code>claw/playbook.md</code> section 11.</p>
+</section>

+<section id="userflow">
+  <h2>User flow (UX)</h2>
+
+  <div class="card">
+    <p><strong>The short version:</strong> the system is a queue, not a loop. It drains <code>01_unprocessed</code> one file at a time and then goes idle. It never reprocesses on its own — a file is touched exactly once, then archived. You "nudge" a re-analysis by putting a file back in the inbox.</p>
+  </div>
+
+  <pre class="mermaid">
+flowchart TD
+    drop["You drop note in 01_unprocessed"] --> trigger["Watcher fires"]
+    trigger --> run["Pipeline processes ONE file"]
+    run --> out["Document appears in 02_processed"]
+    run --> archive["Raw note moved to 03_meta archive"]
+    out --> more{"More files in inbox?"}
+    more -->|"yes"| run
+    more -->|"no"| idle["System idles - zero CPU"]
+    idle -.->|"new file later"| trigger
+  </pre>
+  <p class="diagram-caption">The queue drains, then sleeps. No endless processing, no surprise CPU usage.</p>
+
+  <h3>A file's life</h3>
+  <pre class="mermaid">
+flowchart LR
+    raw["Raw note"] --> queued["Waiting in 01_unprocessed"]
+    queued --> processing["Being processed"]
+    processing --> done["Final doc in 02_processed"]
+    processing --> archived["Original archived in 03_meta"]
+    done -->|"you want changes"| nudge["Copy archived note back to inbox"]
+    nudge --> queued
+  </pre>
+  <p class="diagram-caption">Re-analysis is a deliberate human action: copy the archived original back into the inbox. The new output overwrites the old document.</p>
+
+  <h3>Your daily rhythm</h3>
+  <ol>
+    <li><strong>While coding:</strong> jot rough notes, paste the relevant snippets, save as <code>.md</code> into <code>vault/01_unprocessed/</code>. Don't polish — that's the machine's job. One topic per note.</li>
+    <li><strong>Whenever:</strong> the pipeline picks each note up, one at a time. You don't wait for it.</li>
+    <li><strong>When you need knowledge:</strong> open Obsidian, search or click through links.</li>
+    <li><strong>Weekly-ish:</strong> skim <code>03_meta/backlog.md</code>. It lists what the Critic flagged: contradictions, missing explanations, open questions. Fix the worst ones by editing the archived raw note and dropping it back in the inbox.</li>
+  </ol>
+
+  <h3>How do I nudge a re-analysis?</h3>
+  <table>
+    <tr><th>Situation</th><th>What you do</th></tr>
+    <tr><td>I added more info to a topic</td><td>Edit the archived raw note (in <code>03_meta/archive/</code>), copy it into <code>01_unprocessed/</code>. The pipeline re-runs and overwrites the old document.</td></tr>
+    <tr><td>The output is badly formatted</td><td>Re-run the playbook manually in Claw on that file, or chat with the failing agent's skill directly in Claw with the document as input.</td></tr>
+    <tr><td>I want to merge two notes</td><td>Combine the raw notes into one file yourself, drop it in the inbox, delete the two old documents from <code>02_processed/</code>.</td></tr>
+    <tr><td>Nothing is happening</td><td>Check the daily log (see Logging). If empty, the watcher task isn't running — open Claw and run the playbook manually.</td></tr>
+  </table>
+</section>

+<section id="obsidian">
+  <h2>Obsidian for rookies (and non-technical users)</h2>
+
+  <div class="card">
+    <p>Obsidian is just a viewer/editor for a folder of markdown files. The folder is called a <strong>vault</strong>. In this project, the vault is the repo's <code>vault/</code> folder: open Obsidian, choose <em>"Open folder as vault"</em>, and point it there. That's the entire setup.</p>
+  </div>
+
+  <h3>The four things a reader actually needs</h3>
+  <table>
+    <tr><th>Action</th><th>How</th><th>What it gives you</th></tr>
+    <tr><td>Search everything</td><td><code>Cmd/Ctrl + Shift + F</code></td><td>Full-text search across all processed notes — the number one lookup tool</td></tr>
+    <tr><td>Open a note fast</td><td><code>Cmd/Ctrl + O</code></td><td>Type part of a title, hit Enter</td></tr>
+    <tr><td>Follow connections</td><td>Click any <code>[[linked concept]]</code></td><td>Jump between related topics like a private Wikipedia</td></tr>
+    <tr><td>See the map</td><td>Graph view (icon in the left sidebar)</td><td>A visual map of how all concepts connect — great for spotting clusters and orphans</td></tr>
+  </table>
+
+  <pre class="mermaid">
+flowchart TD
+    q["I have a question"] --> s{"Do I know the topic name?"}
+    s -->|"yes"| quick["Quick open - Cmd O"]
+    s -->|"no"| search["Global search - Cmd Shift F"]
+    quick --> read["Read the Samenvatting"]
+    search --> read
+    read --> enough{"Enough detail?"}
+    enough -->|"yes"| doneNode["Done"]
+    enough -->|"need code"| toggle["Expand the Technical Implementation toggle"]
+    enough -->|"related topic"| link["Click a linked concept"]
+    link --> read
+  </pre>
+  <p class="diagram-caption">Lookup flow for a reader. The documents are designed so non-technical readers stop at the summary, and developers expand the toggles.</p>
+
+  <h3>Why the documents are shaped this way</h3>
+  <ul>
+    <li><strong>Business summary first, in Dutch:</strong> a non-technical colleague reads the top of any note and understands what the thing does and why.</li>
+    <li><strong>Code in collapsed toggles:</strong> readers are never assaulted by a wall of code; developers click once to expand.</li>
+    <li><strong>Wiki links:</strong> concepts like <code>[[Voorraadbeheer]]</code> connect notes automatically. The more notes you process, the more valuable the graph becomes.</li>
+    <li><strong>Diagrams render natively:</strong> Obsidian draws Mermaid blocks as real diagrams, no plugins needed.</li>
+  </ul>
+
+  <div class="card">
+    <p><strong>Rookie warnings:</strong> don't edit files in <code>02_processed/</code> by hand if you ever plan to re-run that note — the pipeline overwrites the file. Make content fixes in the raw note and re-process. And don't rename processed files; wiki links point at filenames.</p>
+  </div>
+</section>

+<section id="msty">
+  <h2>Msty setup: your personal checklist</h2>
+  <p>Full detail lives in <code>claw/playbook.md</code> in the repo. This is the condensed human checklist — do these in order, on each machine.</p>
+
+  <pre class="mermaid">
+flowchart LR
+    p1["1 Providers - models selectable"] --> p2["2 Bot - workspace vault, local only"]
+    p2 --> p3["3 Security - allow vault folder only, network strict"]
+    p3 --> p4["4 Skills - paste 4 prompts"]
+    p4 --> p5["5 Playbook - chain the skills"]
+    p5 --> p6["6 Manual test runs"]
+    p6 --> p7["7 Enable watcher"]
+  </pre>
+  <p class="diagram-caption">Setup order matters: security before skills, manual runs before automation.</p>
+
+  <ol class="checklist">
+    <li><strong>Providers:</strong> Settings &gt; Providers — confirm your llama.cpp models (Gemma/Qwen) appear. Give your strongest model to Agent 1.</li>
+    <li><strong>Bot:</strong> Settings &gt; Bots — one bot. Workspace = Project folder pointed at <code>&lt;REPO&gt;/vault</code>. Runtime = Host. Routing = Local only.</li>
+    <li><strong>Security:</strong> Settings &gt; Security — Allowed Folders: only <code>&lt;REPO&gt;/vault</code> (read/write). Network Guard: Strict. Approvals: on. Do this <em>before</em> the first run, especially at work.</li>
+    <li><strong>Skills:</strong> Settings &gt; Agent Mode &gt; Skills Studio — create folder <code>kb-pipeline</code>, create 8 skills (verifier, structurer, linguist, visualizer, critic, curator, consultant, sentinel), paste each prompt from the repo's <code>agents/</code> files. System prompt mode: Replace.</li>
+    <li><strong>Playbook:</strong> create <code>kb-process-note</code> — agents 1, 2, 7, 3, 4 in sequence (see <code>claw/playbook.md</code> section 5).</li>
+    <li><strong>Test manually:</strong> drop ONE sample note in the inbox, run the playbook by hand, open the result in Obsidian. Check: toggles collapse, diagrams render, links work. Repeat 2-3 times with different notes.</li>
+    <li><strong>Automate:</strong> only when step 6 is reliably clean, create the watcher task on <code>01_unprocessed/</code> (or a 15-minute scheduled run, which is often more robust than a file watcher).</li>
+  </ol>
+</section>

+<section id="logging">
+  <h2>Logging</h2>
+
+  <div class="card">
+    <p><strong>Principle: log metadata, never content.</strong> The logs answer "did the system work, on what, and how well" — without duplicating your notes (which may contain sensitive code) into yet another file.</p>
+  </div>
+
+  <h3>Where and what</h3>
+  <p>One file per day: <code>vault/03_meta/logs/2026-06-11.md</code>. One short block per pipeline run, appended by the playbook:</p>
+
+  <pre class="codeblock">## 14:32 — stock-sync-debounce.md
+- result: success
+- output: 02_processed/stock-sync-debounce.md
+- agents: verifier ok | structurer ok | linguist ok | visualizer ok | critic ok
+- backlog: +2 entries
+- duration: ~4 min
+- source: archived</pre>
+
+  <pre class="mermaid">
+flowchart TD
+    run["Pipeline run finishes"] --> entry["Append entry to today's log file"]
+    entry --> q{"Was there an error?"}
+    q -->|"no"| brief["One short block - metadata only"]
+    q -->|"yes"| verbose["Add error detail - which agent, what failed, what to do"]
+    logs["03_meta/logs/"] --> review["You skim during backlog review"]
+    brief --> logs
+    verbose --> logs
+  </pre>
+  <p class="diagram-caption">Quiet on success, loud on failure — the golden rule of pipeline logging.</p>
+
+  <h3>Calibration: too much vs. too little</h3>
+  <table>
+    <tr><th></th><th>Examples</th><th>Why</th></tr>
+    <tr><td class="bad">Too much</td><td>Full agent inputs/outputs, full prompts, the note's content, per-token traces</td><td>Duplicates sensitive content, bloats the vault, nobody reads it; Claw's own activity view already has run details when you need forensics</td></tr>
+    <tr><td class="good">Right</td><td>Timestamp, filename, per-agent ok/repaired/failed, diagram and flag counts, backlog delta, duration</td><td>Enough to spot trends ("visualizer fails on long notes") and audit what ran without exposing content</td></tr>
+    <tr><td class="bad">Too little</td><td>Just "ran 3 files today"</td><td>Useless when something silently breaks; you can't tell which file or which agent</td></tr>
+  </table>
+
+  <h3>Best practices baked into this design</h3>
+  <ul>
+    <li><strong>Append-only, daily rotation:</strong> never edit old entries; one file per day keeps files small and greppable.</li>
+    <li><strong>Errors are verbose, successes are terse:</strong> a failure entry should say which agent, what broke, and what to do.</li>
+    <li><strong>Logs are local-only:</strong> the <code>.gitignore</code> excludes <code>03_meta/</code> contents (except the backlog template), so logs never get committed.</li>
+    <li><strong>Logs are markdown in the vault:</strong> searchable from inside Obsidian itself with the same search you already use.</li>
+    <li><strong>Retention:</strong> delete log files older than ~3 months whenever you notice them; nothing depends on them.</li>
+  </ul>
+</section>

+<section id="faq">
+  <h2>FAQ</h2>
+  <table>
+    <tr><th>Question</th><th>Answer</th></tr>
+    <tr><td>Does it endlessly process the unprocessed folder?</td><td>No. It processes one file per run, drains the queue, then idles. Files are archived after processing so they're never picked up twice.</td></tr>
+    <tr><td>Can I re-analyze a note?</td><td>Yes — copy the archived raw note from <code>03_meta/archive/</code> back into <code>01_unprocessed/</code>. The new output overwrites the old document.</td></tr>
+    <tr><td>What if a document comes out broken?</td><td>Check the daily log to see which agent misbehaved, then either re-run the playbook on that file or paste the document into a chat with that agent's skill in Claw.</td></tr>
+    <tr><td>Is my company code safe?</td><td>Models run locally via llama.cpp; Network Guard is set to Strict; vault note contents are gitignored. Nothing leaves the machine unless you push it somewhere yourself.</td></tr>
+    <tr><td>How does Cursor use this later?</td><td>A filesystem MCP server pointed at <code>02_processed/</code> gives Cursor read access to the curated knowledge. Config snippet is in the README.</td></tr>
+    <tr><td>Why is half the document in Dutch?</td><td>By design: business concepts in Dutch (with English translations on first use) for non-technical colleagues; technical terms stay in English for developers.</td></tr>
+    <tr><td>How does the wiki get more interlinked over time?</td><td>The Curator (Agent 5) audits documents on a schedule, inserts missing links, and puts missing documents and open questions on the backlog. See "Wiki loop".</td></tr>
+    <tr><td>Can I paste a work ticket and get help?</td><td>Yes — the Consultant (Agent 6) skill. It proposes a plan grounded in the knowledge base and explicitly lists what it doesn't know. Works in Msty chat, or in Cursor via the MCP server.</td></tr>
+    <tr><td>How does the KB stay current when code changes?</td><td>The Sentinel (Agent 8) runs weekly, compares git commits since its last check, writes a changelog, and flags stale documents with <code>#stale-doc</code> on the backlog. You update the raw note and re-process.</td></tr>
+    <tr><td>Who checks the Dutch?</td><td>Agent 7 (Linguist), in the pipeline after the Structurer. It fixes clear Dutch errors and enforces the Dutch/English protocol; uncertain cases get a TAAL callout.</td></tr>
+    <tr><td>Why markdown + Obsidian instead of HTML pages?</td><td>Markdown is the format the agents, RAG, and MCP all consume natively; Obsidian provides search, backlinks, and graph view for free. HTML can always be GENERATED from the markdown later (static site export) — the reverse direction is painful. Markdown stays the source of truth.</td></tr>
+  </table>

+# Sentinel state (template)
+
+Copy this file to `sentinel-state.md` on first setup (same folder).
+`sentinel-state.md` is gitignored — it is machine-specific.
+
+```yaml
+last_commit: ""
+last_checked: ""
+code_repo: "/absolute/path/to/your/work/codebase"
+branch: "main"
+```
+
+The weekly `kb-sentinel-check` playbook reads and overwrites `sentinel-state.md`.
+Point `code_repo` at the application you document — usually NOT this RAGgamuffin
+repo itself, but the Laravel/project repo at work.
