The mental model

Msty Studio is the chat app. Msty Claw is its agent sibling: a desktop app where AI doesn't just answer — it does things: reads and writes files, runs multi-step workflows, on a schedule, with guardrails. RAGgamuffin lives entirely in Claw.

Claw's design philosophy: every automated action runs inside explicit boundaries you set up front — which folders, which network access, which approvals. You define the cage first, then let the agent loose inside it.

The six building blocks and how they relate. Security wraps everything the bot does.

The building blocks

ConceptWhereWhat it isAnalogy
1ProviderSettings > ProvidersA source of models — your local llama.cpp (Gemma/Qwen), optionally cloud APIsThe engine supplier
2BotSettings > BotsAn execution identity: which workspace folder it lives in, Host or Container runtime, local-only or channel routing, what it's allowed to doAn employee with a badge that only opens certain doors
3SkillSettings > Agent Mode > Skills StudioA reusable instruction pack (a system prompt with metadata). Our seven agents are seven skillsA job description
4PlaybookPlaybooksAn ordered, repeatable workflow that chains steps and skills, with success criteriaA standard operating procedure
5TaskTasksA trigger: run a playbook on a schedule or when a folder changes (watcher)The alarm clock
6SecuritySettings > SecurityAllowed folders, blocked patterns, Network Guard (outbound rules), approval checkpointsThe building's keycard system

Key distinction: a skill is knowledge ("how to structure a document"), a playbook is process ("take the oldest file, run these four skills in order, write the results"), a task is timing ("do that whenever a file appears"). Keep them separate in your head and Claw stops being confusing.

Anatomy of a run

What actually happens when the watcher fires on a new note:

sequenceDiagram
    participant T as Task_Watcher
    participant P as Playbook
    participant S as Security
    participant K as Skills
    participant V as Vault
    T->>P: new file detected
    P->>S: may I read 01_unprocessed?
    S-->>P: allowed folder - yes
    P->>K: verifier, structurer, visualizer, critic - in order
    K-->>P: final document plus backlog section
    P->>S: may I write 02_wiki and 03_meta?
    S-->>P: yes - or approval prompt if enabled
    P->>V: write doc, append backlog, append log, archive source

Every file operation passes the security layer. With approvals on, Claw asks you before writing — that's the prompt you'll see during your first runs.

Where to watch it happen: every bot has an Activity view — the full history of what ran, what it read and wrote, and any errors. This is your forensics tool; the daily logs in 03_meta/logs/ are your lightweight summary. Check Activity when a run misbehaves, logs when you just want to know what happened today.

Day-to-day operation

You want to...Do this in Claw
Process notesNothing — drop files in 01_unprocessed/ and the watcher handles it
Run the pipeline right nowOpen the kb-process-note playbook → Run. It exits immediately if the inbox is empty
Audit the wiki nowRun kb-curate manually

Triage a ticketOpen a chat with the kb-consultant skill, paste the ticket. Attach the Knowledge Stack for automatic retrieval
See what ran todayOpen 03_meta/logs/<today>.md in Obsidian — or the bot's Activity view for full detail
Pause the automationDisable the watcher task (Tasks screen). Files just queue up in the inbox; nothing is lost
Improve a promptEdit the file in the repo's agents/, commit, re-paste into the skill on each machine. Repo is the source of truth
Test a prompt change safelyClone the bot or skill, test on a sample note, then promote the change

Approvals: what to expect at first

With the recommended baseline, Claw will interrupt and ask permission for file writes during your first runs. This is intentional — you're verifying the pipeline writes exactly where it should (02_wiki/, 03_meta/) and nowhere else. After several clean runs, relax approvals for writes inside the vault and the pipeline becomes fully hands-off.

The golden rules

  • One bot, one purpose. Don't bolt unrelated jobs onto the KB bot — make a new bot.
  • Security before skills, manual runs before watchers. Always.
  • Never widen Allowed Folders to fix an error; figure out why the playbook tried to write outside the vault instead.
  • After swapping which model backs a skill, re-validate with manual runs — different models break formatting contracts in different ways.
