RAGgamuffin

A local-first, multi-agent assembly line that turns messy coding notes into a clean, structured Obsidian knowledge base. Everything runs on your machine. No data leaves it.

What is this How it works Wiki loop User flow Obsidian guide Msty setup Logging FAQ Claw guide

What is this?

You write rough notes while coding — half sentences, pasted snippets, "remember this gotcha". They pile up and become useless. RAGgamuffin fixes that:

You drop a raw note into a folder. Local AI agents (running via llama.cpp inside Msty Claw) take turns improving it. A finished, structured document appears in your Obsidian vault, with business logic up top, Dutch prose checked, technical code tucked into collapsible toggles, key concepts linked together, and diagrams where they help.

Local-first means private. The models run on your own machine. Company code in your notes never touches a cloud API.

How it works: the assembly line

AgentRoleWhat it doesWhat it must NOT do
1VerifierFact-checkerCompares your prose claims against the code in the note; flags contradictions with warning calloutsNever silently fixes anything
2StructurerEditorBusiness logic first, code hidden in collapsible toggles, key concepts wiki-linked, optional Dutch/English protocolNever changes code content
3VisualizerIllustratorInserts Mermaid flowcharts and sequence diagrams where they clarifyNever rewords a single sentence
4CriticQuality gateRepairs mechanical formatting defects, writes the final file, reports knowledge gaps to the backlogNever touches meaning or code
5CuratorWiki gardener (scheduled)Audits one document at a time: adds missing wiki links, reports missing documents and reader questionsNever changes anything except adding links
6ConsultantTicket triage (interactive)You paste a ticket; it proposes a plan grounded in the knowledge base and lists what info is missingNever presents a guess as knowledge
8SentinelCode watcher (weekly)Compares git commits since last check against the KB; writes a changelog and flags stale documentsNever pastes code diffs or secrets into logs

Agents 1-4 are the lean per-note hot path. Agents 5 and 8 run on a schedule. Agent 6 is interactive.

One pipeline run, from raw note to finished document. Each agent only sees the previous agent's output.

Why a chain of small agents instead of one big prompt?

Small local models (4B-class Gemma/Qwen) do one job well and many jobs badly. Splitting the work means each agent gets a short, strict instruction set and a small context. It also means failures are isolated: if diagrams break, you re-run Agent 3, not the whole thing.

The wiki loop: Curator and Consultant

Processing notes one by one gives you good documents. Two more agents turn those documents into a wiki — an interlinked, self-improving knowledge network.

The Curator (Agent 5) — scheduled gardening

On a schedule (weekly) or on demand, the Curator picks one wiki document and audits it against the entire knowledge base index:

  • Adds missing links: if a document mentions a concept that another document covers, but doesn't link it, the Curator inserts the [[link]]. The graph gets denser over time, automatically.
  • Finds promised-but-missing documents: links pointing at documents that don't exist become #missing-doc backlog entries — your writing TODO list.
  • Asks reader questions: things a reader would wonder after this document that nothing in the base answers become #open-question entries. Answer them yourself or hand them to another LLM, then drop the answer into the inbox as a new note.
flowchart TD
    schedule["Weekly task or manual run"] --> pick["Curator picks one document"]
    pick --> audit["Audit against index of all titles"]
    audit --> links["Insert missing wiki links"]
    audit --> gaps["Report missing documents"]
    audit --> questions["Raise reader questions"]
    gaps --> backlog["Backlog"]
    questions --> backlog
    backlog --> you(("You answer or research"))
    you --> newNote["New raw note in inbox"]
    newNote --> pipeline["Pipeline processes it"]
    pipeline --> denser["Knowledge base grows and interlinks"]
    denser --> pick

The self-improving loop: every audit produces either better linking or new writing prompts. The wiki literally tells you what to write next.

The Consultant (Agent 6) — paste a ticket, get a grounded plan

An interactive skill, not a pipeline stage. Open a chat with it in Msty (with a Knowledge Stack built from 02_wiki/ attached), paste a ticket or task, and it answers in a fixed format:

  1. Wat ik begrijp — its interpretation of the ticket
  2. Voorgestelde aanpak — a concrete plan, citing the knowledge base documents it used
  3. Aannames — every assumption it had to make, explicitly
  4. Ontbrekende informatie — what's missing and who can answer it; structural gaps become #ticket-gap backlog entries

    ticket["You paste a ticket"] --> consultant["Consultant skill"]
    kb["Knowledge Stack from 02_wiki"] --> consultant
    consultant --> plan["Grounded plan of attack"]
    consultant --> missing["Explicit missing-info list"]
    missing --> backlog["Ticket gaps to backlog"]

Real tickets expose the most valuable gaps: knowledge you actually needed and didn't have.

Same trick inside Cursor: with the filesystem MCP server pointed at 02_wiki/ (see README), paste the ticket into Cursor chat and tell it to consult the knowledge base before answering and to list missing information explicitly. Your KB becomes IDE context.

The Sentinel (Agent 8) — weekly code diff check

The codebase moves; the knowledge base can go stale. Once a week the Sentinel compares git history on your work repo against the last commit it checked, writes a changelog, and flags KB documents that likely need updating.

    weekly["Weekly scheduled task"] --> state["Read last_commit from sentinel-state"]
    state --> git["Git log and diff since last commit"]
    git --> sentinel["Sentinel matches changes to KB titles"]
    sentinel --> changelog["Write changelog to 03_meta/changelogs"]
    sentinel --> stale["Flag stale docs on backlog"]

    you --> inbox["Drop back in 01_unprocessed"]
    inbox --> fresh["Pipeline re-processes doc"]

The KB stays tied to the code. Stale-doc backlog entries tell you exactly what to refresh.

Setup: copy sentinel-state.template.md to sentinel-state.md, point code_repo at your Laravel/project repo (not RAGgamuffin itself), add that repo to Claw Allowed Folders as read-only. Full steps in claw/playbook.md section 11.

User flow (UX)

The short version: the system is a queue, not a loop. It drains 01_unprocessed one file at a time and then goes idle. It never reprocesses on its own — a file is touched exactly once, then archived. You "nudge" a re-analysis by putting a file back in the inbox.

flowchart TD
    drop["You drop note in 01_unprocessed"] --> trigger["Watcher fires"]
    trigger --> run["Pipeline processes ONE file"]
    run --> out["Document appears in 02_wiki"]
    run --> archive["Raw note moved to 03_meta archive"]
    out --> more{"More files in inbox?"}
    more -->|"yes"| run
    more -->|"no"| idle["System idles - zero CPU"]
    idle -.->|"new file later"| trigger

The queue drains, then sleeps. No endless processing, no surprise CPU usage.

Re-analysis is a deliberate human action: copy the archived original back into the inbox. The new output overwrites the old document.

Your daily rhythm

  1. While coding: jot rough notes, paste the relevant snippets, save as .md into vault/01_unprocessed/. Don't polish — that's the machine's job. One topic per note.
  2. Whenever: the pipeline picks each note up, one at a time. You don't wait for it.
  3. When you need knowledge: open Obsidian, search or click through links.
  4. Weekly-ish: skim 03_meta/backlog.md. It lists what the Critic flagged: contradictions, missing explanations, open questions. Fix the worst ones by editing the archived raw note and dropping it back in the inbox.

How do I nudge a re-analysis?

SituationWhat you do
I added more info to a topicEdit the archived raw note (in 03_meta/archive/), copy it into 01_unprocessed/. The pipeline re-runs and overwrites the old document.
The output is badly formattedRe-run the playbook manually in Claw on that file, or chat with the failing agent's skill directly in Claw with the document as input.
I want to merge two notesCombine the raw notes into one file yourself, drop it in the inbox, delete the two old documents from 02_wiki/.
Nothing is happeningCheck the daily log (see Logging). If empty, the watcher task isn't running — open Claw and run the playbook manually.

Obsidian for rookies (and non-technical users)

Obsidian is just a viewer/editor for a folder of markdown files. The folder is called a vault. In this project, the vault is the repo's vault/ folder: open Obsidian, choose "Open folder as vault", and point it there. That's the entire setup.

See the mapGraph view (icon in the left sidebar)A visual map of how all concepts connect — great for spotting clusters and orphans

Lookup flow for a reader. The documents are designed so non-technical readers stop at the summary, and developers expand the toggles.

Why the documents are shaped this way

  • Business summary first: a non-technical colleague reads the top of any note and understands what the thing does and why (optionally in Dutch with English translations).
  • Code in collapsed toggles: readers are never assaulted by a wall of code; developers click once to expand.
  • Wiki links: concepts like [[Voorraadbeheer]] connect notes automatically. The more notes you process, the more valuable the graph becomes.
  • Diagrams render natively: Obsidian draws Mermaid blocks as real diagrams, no plugins needed.

Rookie warnings: don't edit files in 02_wiki/ by hand if you ever plan to re-run that note — the pipeline overwrites them. Edit the archived raw note in 03_meta/archive/ instead. Don't rename wiki files; links point at filenames.

Msty setup: your personal checklist

Full detail lives in claw/playbook.md in the repo. This is the condensed human checklist — do these in order, on each machine.

flowchart LR
    p1["1 Providers - models selectable"] --> p2["2 Bot - workspace vault, local only"]
    p2 --> p3["3 Security - allow vault folder only, network strict"]
    p3 --> p4["4 Skills - paste 4 prompts"]
    p4 --> p5["5 Playbook - chain the skills"]
    p5 --> p6["6 Manual test runs"]
    p6 --> p7["7 Enable watcher"]

Setup order matters: security before skills, manual runs before automation.

  1. Providers: Settings > Providers — confirm your llama.cpp models (Gemma/Qwen) appear. Give your strongest model to Agent 1.
  2. Bot: Settings > Bots — one bot. Workspace = Project folder pointed at <REPO>/vault. Runtime = Host. Routing = Local only.
  3. Security: Settings > Security — Allowed Folders: only <REPO>/vault (read/write). Network Guard: Strict. Approvals: on. Do this before the first run, especially at work.
  4. Skills: Settings > Agent Mode > Skills Studio — create folder kb-pipeline, create 7 skills (verifier, structurer, visualizer, critic, curator, consultant, sentinel), paste each prompt from the repo's agents/ files. System prompt mode: Replace.
  5. Playbook: create kb-process-note — agents 1, 2, 3, 4 in sequence (see claw/playbook.md section 5).
  6. Test manually: drop ONE sample note in the inbox, run the playbook by hand, open the result in Obsidian. Check: toggles collapse, diagrams render, links work. Repeat 2-3 times with different notes.
  7. Automate: only when step 6 is reliably clean, create the watcher task on 01_unprocessed/ (or a 15-minute scheduled run, which is often more robust than a file watcher).

Logging

Principle: log metadata, never content. The logs answer "did the system work, on what, and how well" — without duplicating your notes (which may contain sensitive code) into yet another file.

Where and what

One file per day: vault/03_meta/logs/2026-06-11.md. One short block per pipeline run, appended by the playbook:

## 14:32 — stock-sync-debounce.md
- result: success
- output: 02_wiki/stock-sync-debounce.md
- agents: verifier ok | structurer ok | visualizer ok | critic ok
- backlog: +2 entries
- duration: ~4 min
- source: archived
flowchart TD
    run["Pipeline run finishes"] --> entry["Append entry to today's log file"]
    entry --> q{"Was there an error?"}
    q -->|"no"| brief["One short block - metadata only"]
    q -->|"yes"| verbose["Add error detail - which agent, what failed, what to do"]
    logs["03_meta/logs/"] --> review["You skim during backlog review"]
    brief --> logs
    verbose --> logs

Quiet on success, loud on failure — the golden rule of pipeline logging.

Calibration: too much vs. too little

ExamplesWhy
Too muchFull agent inputs/outputs, full prompts, the note's content, per-token tracesDuplicates sensitive content, bloats the vault, nobody reads it; Claw's own activity view already has run details when you need forensics
RightTimestamp, filename, per-agent ok/repaired/failed, diagram and flag counts, backlog delta, durationEnough to spot trends ("visualizer fails on long notes") and audit what ran without exposing content
Too littleJust "ran 3 files today"Useless when something silently breaks; you can't tell which file or which agent

Best practices baked into this design

  • Append-only, daily rotation: never edit old entries; one file per day keeps files small and greppable.
  • Errors are verbose, successes are terse: a failure entry should say which agent, what broke, and what to do.
  • Logs are local-only: the .gitignore excludes 03_meta/ contents (except the backlog template), so logs never get committed.
  • Logs are markdown in the vault: searchable from inside Obsidian itself with the same search you already use.
  • Retention: delete log files older than ~3 months whenever you notice them; nothing depends on them.

FAQ

QuestionAnswer
Does it endlessly process the unprocessed folder?No. It processes one file per run, drains the queue, then idles. Files are archived after processing so they're never picked up twice.
Can I re-analyze a note?Yes — copy the archived raw note from 03_meta/archive/ back into 01_unprocessed/. The new output overwrites the old document.
What if a document comes out broken?Check the daily log to see which agent misbehaved, then either re-run the playbook on that file or paste the document into a chat with that agent's skill in Claw.
Is my company code safe?Models run locally via llama.cpp; Network Guard is set to Strict; vault note contents are gitignored. Nothing leaves the machine unless you push it somewhere yourself.
How does Cursor use this later?A filesystem MCP server pointed at 02_wiki/ gives Cursor read access to the curated knowledge. Config snippet is in the README.
Why is half the document in Dutch?By design: business concepts in Dutch (with English translations on first use) for non-technical colleagues; technical terms stay in English for developers.
How does the wiki get more interlinked over time?The Curator (Agent 5) audits documents on a schedule, inserts missing links, and puts missing documents and open questions on the backlog. See "Wiki loop".
Can I paste a work ticket and get help?Yes — the Consultant (Agent 6) skill. It proposes a plan grounded in the knowledge base and explicitly lists what it doesn't know. Works in Msty chat, or in Cursor via the MCP server.
How does the KB stay current when code changes?The Sentinel (Agent 8) runs weekly, compares git commits since its last check, writes a changelog, and flags stale documents with #stale-doc on the backlog. You update the raw note and re-process.
Who checks the Dutch?The Structurer (Agent 2) owns the optional Dutch/English protocol. It is a clearly-marked, removable block in that prompt — delete it for English-only docs in phase 1, keep it if you want bilingual business prose.
Why markdown + Obsidian instead of HTML pages?Markdown is the format the agents, RAG, and MCP all consume natively; Obsidian provides search, backlinks, and graph view for free. HTML can always be GENERATED from the markdown later (static site export) — the reverse direction is painful. Markdown stays the source of truth.
